**The suggested opt-out does not protect a publishing reader.** Issue #1034 asks to map `save-cache: false` as the publishing opt-out. The action's deployed `dist/setup/index.js` was executed unchanged against an isolated localhost cache-service fixture. With `save-cache: false`, it sent `GetCacheEntryDownloadURL` with both its full key and broad restore prefix. `node investigation/fixture-probe.cjs restore-only --expect-no-read` fails with `restore-only publishing still reads cache; true !== false`; its child action itself exits 0. Changing only the fixture to `github-cache: false`, without S3, produces zero cache-service requests and passes. This is a genuine fixture discriminator, not a mutation of the implementation. The service deliberately returns a cache miss: this proves a reachable read request, not malicious archive execution.

The S3 fixture executes the same shipped setup bundle with `save-cache: false` and `sync: true`: it invokes `sync --pull`, `daemon start`, and `stats`, while rendering `[cache] remote_readonly = true`. Its Kache executable is a recording fixture, so this proves the action's command/config behavior, not an actual S3 download. Source confirms the same result: `src/setup.js:280` switches off uploads, `:346` still pulls/restores, and `:361` still starts prefetch. `src/save.js:30` skips post-step saves. The README already accurately describes restore-only behavior at lines 117–125; the error is the issue's proposed use of that behavior for a publishing sink. The baseline `src/config.rs:369` explicitly defines remote read-only as preserving reads/restores; `src/wrapper/remote.rs:12` gates uploads, while `acquire_entry` still requests a remote entry.

zizmor's actions/cache control is `lookup-only`, which skips downloading a found cache. It is semantically different from `save-cache`. Registering kache-action with `save-cache` as the suppression toggle would hide the demonstrated reader. A GitHub-cache-only opt-out could instead use `github-cache: false`, but that input does not disable S3 or a configured shared local store, so it cannot safely serve as a universal toggle for the action. Registration should represent the backends accurately or avoid proposing a universal Boolean auto-fix. No patch or upstream submission was made.

**Practical trust boundaries and affected workloads.** The current [GitHub dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache) limits ordinary fork-PR caches to the PR merge ref; release/default-branch jobs cannot restore them. This rules out a generic claim that merely opening a normal fork PR can poison a release cache. Default-branch and same-ref caches can be shared across workflows. The action key includes version, OS/arch and lockfile hash, and its restore prefix omits the lockfile hash (`src/utils.js:551`); those are reuse partitions, not writer authentication.

GitHub's current policy also gives low-trust default-branch triggers, including `pull_request_target`, `issue_comment` and `workflow_run`, read-only cache access by default. An explicit write-capable `cache-mode` overrides that restriction. `fixtures/untrusted-source-github.yml` names that required override and an untrusted PR-head checkout followed by Cargo execution. It is a reachable workflow configuration, not an executed hosted attack. In such a misconfigured source job, arbitrary build-script code can alter the local cache or use its cache token directly; the action's save path is outside Kache's remote-upload guard. A publishing sink that restores from the same default-branch cache remains exposed to whatever entries that authorized writer can introduce. A protected push workflow with arbitrary untrusted input can also be a source; the writer's trust must be evaluated, not inferred from a key name.

S3 is a separate boundary: GitHub's cache-mode token policy does not apply to S3 credentials, prefixes or a shared node-local mount. A source job with object-write authority to a prefix later read by releases creates a similar conditional risk. Kache's own forced-readonly policy offers useful default behavior: an executed stdlib-only probe compiles the unchanged baseline `src/policy.rs` and observes readonly for PR, PR-target, workflow-run, release/tag and unprotected push, with writes allowed for a protected-branch push. Config also permits a distinct configured PR prefix at `src/config.rs:2103`. These program guards neither revoke an S3 credential nor authenticate reads: arbitrary code already executing in the job can use credentials directly. Restrict writes with actual backend permissions and separate trusted/untrusted storage. No IAM bypass or prefix escape was established here.

The publishing sink should avoid restoring untrusted build state. Omitting the kache-action step from a fresh release build is the clearest backend-independent option. For the GitHub backend, current `cache-mode: none` provides service-enforced access denial; `github-cache: false` also prevents this action's restore call, as tested. Neither setting controls S3. Read-only credentials and `save-cache: false` are valuable source-write controls but preserve the sink's read exposure. See [zizmor's cache-poisoning documentation](https://docs.zizmor.sh/audits/#cache-poisoning), which explicitly treats compromised reads in publishing workflows as the sink concern. New cache-mode-aware behavior in current zizmor main is documented for 1.31.0; it was not executed using the 1.30.1 binary.
