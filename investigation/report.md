`qa-remote-binding`: the test normally publishes two valid entries of the same crate: source A returns `11`, and source B returns `29`. Their generated keys are distinct. For the cold request of A, the loopback endpoint returns the complete B pack under A's object path; it does not modify metadata, artifacts, hashes or pack structure. The daemon commits A's requested row with B's metadata, and the wrapper restores the rlib as a `RemoteHit`. A directly compiled and executed consumer prints `29`. The independent expected value is `11`, from the source being compiled. The test fails with `AssertionError: WRONG_REMOTE_BINDING: source returns 11 but restored valid artifact returns 29`. [The full execution log](binding-swap.execution.txt) records the requested and imported keys, committed row, wrapper restore, consumer argv, output and assertion; [the daemon log](binding-swap.cold.daemon.log) records the real exact-download path.

`qa-cross-shard-singleflight`: a fresh daemon has main and configured shard stores. Two same-key checks independently name the respective valid store/entry directories. In the concurrent batch case, both responses are exactly `{"found":true,"ok":true}`, but read-only SQLite queries observe `main_committed: True shard_committed: False`. Reversing request order reverses the missing store: main False, shard True. The test also fails with two independent socket connections carrying normal `RemoteCheck` requests. [The batch execution](shards-concurrent.execution.txt), [reverse execution](shards-reverse.execution.txt), and [independent-client execution](shards-sockets.execution.txt) preserve the requests, replies, committed-row checks and the red assertion `SHARD_SINGLEFLIGHT_FALSE_HIT: both requests report found but a requested store has no committed entry`.

The cause is `handle_remote_check_started_at` (`src/daemon.rs:4481-4533`): it validates and resolves each requested store, then calls `remote_checks.claim(&req.key)` without destination identity. Followers return the leader `Response` verbatim; only the leader imports into its own resolved `cache_dir`. The real socket dispatcher admits both individual and batch requests (`src/daemon.rs:8698-8712`), and batch handling runs the checks concurrently (`src/daemon.rs:4968-4980`). Compiler wrappers populate the shard argument from the chosen store (`src/wrapper/remote.rs:49-57`). They reload their own store after the reply (`src/wrapper/remote.rs:66`); `Store.get` returns None when its committed row is absent (`crates/kache-store/src/store.rs:2450-2457`). Therefore safe local recompilation/lost reuse is the source-supported consumer consequence. No wrong compiler artifact or data loss is attributed to this scheduling defect, and recompilation duration/frequency was not measured. The two test stores are distinct configured directories on the same physical volume; native multi-volume routing was not reproduced.
