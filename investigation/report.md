Issue [#327](https://github.com/kunobi-ninja/kache/issues/327) has a reproducible, consequential request-saturation case on baseline 4ee0f9e2b9673aa16f29c9c7e39bf8d0152671d9. It is a measured scheduling cost and feature-design input, with zero admitted correctness defects. The 512 MiB download-memory budget does not admit current entry-pack restores: they stream through `get_into` to disk. Sixteen demand restores can therefore occupy the default sixteen request permits regardless of their total pack size. The separate prefetch gate still protects a demand reserve (12 speculative requests out of 16); demand itself can fill the entire pool.

Executed evidence:

| Workload | Observed tiny request outcome | Endpoint evidence |
|---|---|---|
| Pool 4, 3 held ~1 MiB packs, tiny caller budget 1 s | Hit, 766 ms | One tiny GET; direct HEAD 1 ms |
| Pool 4, 4 held ~1 MiB packs, tiny caller budget 1 s | Miss, 1002 ms | Zero tiny GETs; direct HEAD 0 ms |
| Pool 16, 15 held ~32 MiB packs, tiny caller budget 1 s | Hit, 789 ms | One tiny GET; direct HEAD 0 ms |
| Pool 16, 16 held ~32 MiB packs, tiny caller budget 1 s | Miss, 1000 ms | Zero tiny GETs; direct HEAD 0 ms |
| Pool 16, 16 held ~32 MiB packs, uniform 3 s tiny caller | Hit, 2255 ms | One tiny GET; direct HEAD 0 ms |

The sixteen large objects total 536,916,528 compressed bytes. All sixteen real S3 body streams opened. If this path instead used buffered `get` with the same 8 GiB per-object cap, each request would reserve the entire 536,870,912-byte budget (the reservation is derived from the supplied cap, doubled and clamped), allowing one buffered object at a time. This demonstrates request occupancy outside that buffered budget; it does not demonstrate client heap growth. The HTTP fixture streams headers plus the first KiB of valid Store/RemoteLayout-produced packs and holds their tails until cleanup. It serves small packs promptly and uses disk-backed file handles, so endpoint unresponsiveness, corrupt pack bytes, and a server-side 512 MiB allocation are not explanations for the tiny queue miss.

The one-second caller is a supported production case, not the uniform default: `send_remote_check` embeds the client's configured deadline, and the daemon honours the stricter client/daemon budget. For example, a client configured for one second can talk to an existing daemon configured for thirty seconds. Every synchronous demand is still capped at three seconds. The default-budget control successfully restores the tiny pack, establishing bounded delay rather than indefinite starvation.

A second consequence persists after saturation clears. In the four-permit workload, three distinct one-second callers expire while waiting for the local semaphore and issue no remote GET. Their failures open the shared read-direction breaker. After all four occupied demands are aborted and awaited, public daemon stats report `total=4 used=0`. The endpoint answers HEAD, but a fourth distinct valid tiny key still returns a miss with zero GETs. The one-free-permit discriminator serves all three tiny callers and the recovery caller. The default breaker threshold is three and its cooldown is forty-five seconds (`src/remote_resilience.rs:360-364`); immediate post-release suppression is executed evidence, while the duration comes from pinned production source. This turns a brief local queue overload into later read suppression across keys. Writes use a separate breaker.

These observations make a scheduling change worth evaluating for concurrent cold Cargo builds and clients with tighter deadlines. They do not establish that weighted permits are the right change. The behavior is an explicit best-effort deadline/breaker policy, and the current issue is a feature request without a binding small-operation latency promise. Accordingly, both costs are tagged `polish`, `measured-cost`, `no-action` in `findings.json`, with no admitted `defect` or `gap`. A class reserve or priority policy and whether local queue timeouts should affect remote health deserve separate design evaluation. Merely replacing `acquire` with `acquire_many` does not promise small-operation priority: Tokio [documents FIFO fairness](https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html) that can let a bulk waiter block a later single-permit waiter. No modified implementation was benchmarked.

The production path is `send_remote_check` (`src/daemon.rs:9088`) → socket RemoteCheck dispatch → `handle_remote_check_started_at` → `handle_remote_check_leader` → one-permit demand queue (`src/daemon.rs:4765`) → `V3Remote.download_entry` (`src/cache_remote.rs:122`) → `RemoteLayout.download_entry_observed` (`src/remote_layout.rs:147`) → `OpenDalBackend.get_into/read_into` (`src/remote_backend.rs:538/406`) → temporary disk spool → verification/import or deadline miss. Buffered `get/get_versioned` acquire `DownloadMemory`; streaming `get_into` does not. Queue timeout feeds `BreakerPermit.failure` at `src/daemon.rs:4779`, and later demands consult the breaker at `src/daemon.rs:4752`.
