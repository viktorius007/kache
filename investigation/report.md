Confirmed finding EV594-001: a full batch of unrecoverable zero-cost entries can starve recoverable expensive legacy entries in compile-time backfill. `ArtifactStore::backfill_compile_times_limited`, `crates/kache-store/src/store.rs:5491`, selects up to 10,000 committed zero-valued index rows without a cursor or a fair selection rule. Only positive metadata costs remove a row from that selection. Valid zero-cost metadata remains eligible. In the executed fixture, three successive public `backfill_compile_times()` calls each returned zero, and a later entry whose metadata says 60,000 ms remained indexed as zero. Red assertion: expected 60000, received 0. This is a migration-progress defect, not an unknown-cost policy choice.

The independently executed fixture discriminator was the blocking cohort size: 10,000 valid zero-cost rows produce `[0, 0, 0]` updates; 9,999 produce `[1, 0, 0]`, and the expensive entry is restored to 60,000 ms. Both cases use valid deserializable metadata, committed entries, an existing shared artifact blob, correct entry mappings/refcounts, and the production batch constant through the public API. No production hook, fix, or known-failing suite test was added. The standalone test and manifest are embedded in `findings.json` and retained in `harness/`.

Affected workloads are large pre-index stores whose batch prefix contains at least 10,000 entries with genuinely zero/absent compile cost, or metadata that cannot yield a positive cost. The zero-cost case is proved; the unreadable-metadata variant follows the same source branch but was not separately executed. This can bias observations and block completion of the measurement prerequisite for a policy decision. Severity drivers are persistent migration/data-quality failure on large legacy stores; no direct live-policy change or artifact-integrity failure is proved.
