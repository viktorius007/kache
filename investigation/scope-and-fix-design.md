# D5 production reachability and proposed fix scope

Baseline: `4ee0f9e2b9673aa16f29c9c7e39bf8d0152671d9`. No production changes.

The reachable trigger is an actual successful PUT of an absent remote key. The key-already-present branch returns at `src/daemon.rs:4243` without post-upload pressure GC; failed/suppressed/readonly uploads do not reach it. The real PUT success branch records transfer statistics, publishes key presence, retires the intent, then calls inline GC at `src/daemon.rs:4344`. Size pressure/backoff controls whether eviction runs, after the helper has attempted maintenance, GC lock acquisition and a size query (`6743–6837`).

Rust compile publication reaches the path through `src/wrapper.rs:4952` → `src/wrapper/remote.rs:16–30` → `send_upload_job` (`src/daemon.rs:8832–8912`). The wrapper synchronously persists a durable intent (`8853`), taking the store's GC lock (`724–778`), then sends a fire-and-forget socket request. In server mode `handle_upload` acknowledges enqueueing (`4014–4057`); `server_main` runs an unbounded buffer, bounded channel, and `max(s3_concurrency,1)` async upload tasks (`7384–7437`). The configured default is 16 upload tasks (`src/config.rs:1815–1827`), independent of the runtime's worker-thread count. Startup replay uses the same durable-job worker path. `next_upload_job` releases the shared channel receiver mutex before processing each job (`7310–7314`).

Thus GC occupies a background upload slot until `do_upload` completes, rather than making the enqueue response wait for that PUT/GC. Other clients submitting new durable intents can still wait for the shared GC lock; this happens with offloaded GC as well, so this investigation does not attribute that cost solely to inline scheduling. Actual whole-Cargo makespan was not measured.

The main pressure sweep releases the daemon Store mutex before eviction (`6769–6784`), while retaining a per-store GC lock. Other pressure sweeps of that same store skip a held lock. Multiple worktrees sharing one store do not create independent full sweeps. Configured `[cache.volumes]` stores have their own lock and budget (`src/volume_gc.rs`, `src/config.rs:3053–3065`). Every post-upload trigger also scans those shard configurations. After one upload blocks sweeping the main store, another can skip that lock and sweep a shard (`6743–6764`). The exclusive lock bounds simultaneous eviction holders per store, not per daemon; it does not bound every synchronous store-open, file operation or mutex wait elsewhere in the call chain.

The foreground daemon constructs a multithread Tokio runtime without overriding its worker count (`src/daemon.rs:7224–7227`). Tokio 1.53.1 is pinned in Cargo.lock. Tokio's documented default follows available cores, and `TOKIO_WORKER_THREADS` can override the default: [Builder worker_threads](https://docs.rs/tokio/1.53.1/tokio/runtime/struct.Builder.html#method.worker_threads). A one-worker runtime or a two-worker runtime with two pressured stores is supported configuration. Nothing here establishes starvation from one sweep in an otherwise idle 16-worker daemon.

The sweep also intentionally sleeps synchronously to pace database writes: production defaults are a 50 ms write slice and a 150 ms stand-off (`crates/kache-store/src/store.rs:1206–1212`); `apply_eviction` uses `std::thread::sleep` after write slices or contention (`4940–4975`). These pauses help SQLite writers progress while still occupying the calling async worker. This is source evidence of the mechanism; it does not measure ordinary build frequency or imply every sweep incurs a pause.

## Minimal coherent fix design, for later approval

Use the existing coalesced GC-hint scheduler for post-upload maintenance. After successful PUT/key-presence publication/intent retirement, request the same blocking-pool sweep instead of invoking `sweep_under_size_pressure` inline. Share the `gc_hint_pending` claim and unwind-safe release with the GC-hint driver, so upload bursts enqueue at most one daemon-wide pressure sweep, including all volume stores. Keep the cross-process per-store locks, size trigger, backoff, disk-recovery checks and reporting inside the existing sweep helper. No sweep algorithm changes are needed.

The existing GC-hint entry point needs `&Arc<Daemon>` to own the task's lifetime. An implementation should therefore give the async upload chain Arc-capable receivers (`handle_upload`, `do_upload`, and the worker helper), adapt direct test callers mechanically, and reuse the scheduler body. This is a receiver/lifetime adjustment, not a second copy of the eviction implementation. Avoid a daemon recreated just for GC, an unbounded new task per PUT, or a second independent pending bit. Reusing the hint driver changes upload-job completion to mean remote publication/intent retirement is complete while opportunistic local maintenance can still be running; that is consistent with its background nature, and the health regression should assert eventual GC completion/eviction separately.

A one-site `block_in_place` call can protect other spawned tasks on a multithread runtime, but is a less suitable default: it still occupies the upload slot, suspends joined work in the same task, and panics in current-thread runtimes used by direct upload tests. [Tokio 1.53.1 block_in_place](https://docs.rs/tokio/1.53.1/tokio/task/fn.block_in_place.html). `spawn_blocking` supports current-thread runtimes, but running blocking tasks cannot be aborted and shutdown must account for their lifetime. [Tokio 1.53.1 spawn_blocking](https://docs.rs/tokio/1.53.1/tokio/task/fn.spawn_blocking.html). The daemon already uses a one-second runtime shutdown timeout (`src/daemon.rs:7231–7242`); a later fix must retain its lifecycle behavior.

Acceptance tests for a later implementation: the existing one-worker health-before-writer-release regression becomes green; the report-only main+shard/two-worker regression becomes green; successful upload, durable intent retirement and eventual victim eviction/reporting still occur; existing held-GC-lock and pressure/backoff tests remain green; overlapping hints and upload completions coalesce and a later hint is admitted after sweep completion or unwind; startup replay and shutdown still drain upload publication without waiting indefinitely for opportunistic GC. No fix was implemented or tested in this investigation.
